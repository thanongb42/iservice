เรียนรู้ Cron: จาก Linux crontab สู่ Self-Service Web Scheduler

บันทึกนี้ตั้งใจเขียนแบบสอนตัวเอง (learning notes) — เป้าหมายคือเข้าใจหลักการของ cron ก่อนใช้เครื่องมือสำเร็จรูป ไม่ใช่แค่ copy คำสั่งมาวางแล้วใช้งานได้โดยไม่รู้ว่าทำงานอย่างไร

1. Linux crontab ทำงานอย่างไร

cron คือ daemon ที่รันอยู่บน Linux ตลอดเวลา (background process) มันจะตื่นขึ้นมาเช็คทุก ๆ 1 นาที ว่ามี job ไหนถึงเวลาต้องรันบ้าง โดยอ่าน schedule จากไฟล์ที่เรียกว่า crontab ของแต่ละ user

รูปแบบ 1 บรรทัดใน crontab:


*    *    *    *    *    command-to-run
┬    ┬    ┬    ┬    ┬
│    │    │    │    └── วันในสัปดาห์ (0-7, 0 และ 7 = อาทิตย์)
│    │    │    └─────── เดือน (1-12)
│    │    └──────────── วันในเดือน (1-31)
│    └───────────────── ชั่วโมง (0-23)
└────────────────────── นาที (0-59)

ตัวอย่างที่ใช้จริงในโปรเจกต์นี้:


*/15 * * * *   = ทุก 15 นาที (นาทีที่หาร 15 ลงตัว คือ :00, :15, :30, :45 — ตรงเวลานาฬิกาเสมอ ไม่ใช่นับถอยจากตอนติดตั้ง)
5 0 * * *      = ทุกวัน เวลา 00:05
* * * * *      = ทุกนาที (ใช้กับ cron/runner.php ที่สร้างขึ้นใหม่)

จุดสำคัญที่มักเข้าใจผิด: */15 ไม่ได้หมายความว่า "15 นาทีถัดจากตอนนี้" แต่หมายถึง "ทุกค่าที่หารด้วย 15 ลงตัว นับจากนาทีที่ 0 ของทุกชั่วโมง" เพราะฉะนั้นไม่ว่าจะติดตั้ง crontab เวลาไหน ก็จะไปชนที่ :00 :15 :30 :45 เสมอ — เป็นเหตุผลที่ตอบคำถาม "อยากให้รันตรงเวลา 09:00, 09:15, ... ไม่ใช่นับจากตอนนี้" ได้ตรงไปตรงมา (ดู ช่วงก่อนหน้า ที่เปลี่ยนจาก */5 เป็น */15)

คำสั่งจัดการ crontab ที่ใช้บ่อยในโปรเจกต์นี้:


crontab -l                 # ดู schedule ทั้งหมดของ user ปัจจุบัน
crontab -e                 # แก้ไขแบบเปิด editor (เช่น nano)
crontab -l | crontab -     # อ่านของเดิมแล้วเขียนกลับ (ใช้คู่กับ echo/grep ต่อ pipe เพื่อแก้แบบไม่ต้องเปิด editor)

2. ทำไมเดิมใช้ cron-job.org (SaaS ภายนอก)

ก่อนเรียนรู้เรื่อง crontab ของ VM1 เอง โปรเจกต์ใช้ cron-job.org เป็นตัวยิง HTTP request ไปที่ pm25_cron.php ทุก 5 นาที วิธีนี้มีข้อดีคือตั้งง่าย ไม่ต้อง SSH ไม่ต้องรู้จัก Linux crontab เลย แต่มีข้อเสียคือ:

  • พึ่งพาบริการนอก — ถ้า cron-job.org ล่ม/โดนจำกัด rate/หยุดให้บริการ ระบบเราก็หยุดทำงานไปด้วย โดยที่เราควบคุมไม่ได้
  • ข้อมูล credential/URL ปลายทางของเราต้องไปฝากไว้กับบริการภายนอก
  • ดู response/log ของการรันแต่ละครั้งได้จำกัดตามที่ dashboard ของเขาให้ดู

3. ย้ายมารัน crontab ตรงบน VM1

ขั้นแรกของการเรียนรู้คือเลิกพึ่ง cron-job.org แล้วตั้ง crontab ของ user rssc บน VM1 ให้ยิง URL เดิมเอง:


*/15 * * * * cd /home/rssc/web-server && sudo docker compose exec -T php-app php /var/www/html/iservice/pm25_cron.php >> /home/rssc/pm25_cron_trigger.log 2>&1

จุดที่ต้องระวังตอนทำจริง (เจอเองระหว่างตั้งค่า):

  • docker compose exec ต้อง cd ไปโฟลเดอร์ที่มี docker-compose.yml ก่อน ไม่งั้นหาคอนเทนเนอร์ไม่เจอ
  • ต้องใส่ -T เพื่อปิด pseudo-tty เพราะ cron รันแบบไม่มี terminal โต้ตอบ — ถ้าไม่ใส่จะ error "the input device is not a TTY"
  • sudo ใน crontab ใช้ได้เฉพาะถ้า user มี NOPASSWD ตั้งไว้ใน sudoers (เช็คด้วย sudo -n docker ps — ถ้าไม่ต้องใส่ password ก็ใช้ได้)
  • คำสั่ง sed ที่ใช้แก้ไข crontab แบบ in-place ต้องเขียน pattern ให้เจาะจงพอ ไม่งั้นจะไปแก้ entry ของ project อื่นที่ดันมี pattern ตรงกันโดยไม่ตั้งใจ (เกือบเกิดขึ้นจริงตอนเปลี่ยน */5 เป็น */15 — บังเอิญรอดเพราะ entry อื่นตั้งค่าตรงกันอยู่แล้ว แต่เป็นบทเรียนว่าควรใช้ grep filter เฉพาะบรรทัดที่ต้องการ ไม่ใช่ sed แบบกว้าง)

4. หลักการ "Virtual Cron": ทำไมไม่แก้ OS crontab ตรง ๆ ทุกครั้ง

หลังจากย้ายมาอยู่บน VM1 แล้ว ทุกครั้งที่จะเพิ่ม/ลบ/แก้ schedule ของ job ใหม่ ต้อง SSH เข้าไปแก้ crontab เอง — ใช้ได้สำหรับงานของแอดมินที่คุ้นเคยกับ Linux แต่ไม่เหมาะกับการเปิดให้คนอื่นจัดการเอง (ไม่อยากให้ทุกคนต้องมี SSH access)

วิธีแก้ปัญหานี้แบบสากล (ใช้ในระบบจัดการ job หลายเจ้า เช่น Laravel Scheduler, Django-Celery-Beat) คือ Virtual Cron / Database-Driven Scheduler:


แทนที่จะมี:
  crontab entry 1 ตัวต่อ 1 job  (ต้องแก้ไฟล์ระบบทุกครั้งที่เพิ่ม/ลบ job)

ใช้แบบนี้แทน:
  crontab entry เดียว ที่รันทุกนาที (* * * * *)
       │
       ▼
  เรียก runner.php
       │
       ▼
  runner.php query ตาราง DB (cron_schedules)
  หา job ที่ "ถึงเวลาแล้ว" ตาม interval ที่ตั้งไว้
       │
       ▼
  ยิง HTTP request ไปที่ target_url ของ job นั้น ๆ
  บันทึกผลลัพธ์ (success/error, http code, เวลาที่ใช้) กลับเข้า DB

ข้อดีของแนวทางนี้:

  • แก้ schedule ผ่านหน้าเว็บได้เลย — เพิ่ม/ลบ/เปลี่ยนความถี่ของ job ก็แค่ INSERT/UPDATE/DELETE แถวใน DB ไม่ต้องแตะ crontab ของระบบปฏิบัติการอีก
  • มีประวัติการรันเก็บไว้ใน DB (cron_schedule_runs) — ย้อนดูได้ว่า job ไหนรันสำเร็จ/ล้มเหลวกี่ครั้ง เมื่อไหร่ ใช้เวลานานแค่ไหน ต่างจาก SSH ดู log ไฟล์ที่ grep เองทุกครั้ง
  • เปิดสิทธิ์ให้ non-technical user จัดการ job ได้ โดยไม่ต้องให้ SSH access เข้าเซิร์ฟเวอร์เลย — เหมาะกับการเปิดให้แอดมิน iService ทั่วไปใช้ ไม่จำเป็นต้องเป็นคนที่ดูแล VM1 โดยตรง

ข้อเสีย/ข้อจำกัดที่ต้องรู้:

  • ความละเอียดของเวลาจำกัดที่ 1 นาที — เพราะ runner ถูกเรียกทุก 1 นาทีเท่านั้น ถ้าต้องการ schedule ที่ละเอียดกว่านาที (เช่น ทุก 10 วินาที) ต้องใช้วิธีอื่น ไม่ใช่ pattern นี้
  • ยังต้องมี crontab entry จริง 1 บรรทัดอยู่ดี (ตัวที่เรียก runner.php) — Virtual Cron ไม่ได้ทำให้ไม่ต้องใช้ OS cron เลย แค่ลดจำนวน entry ที่ต้องแก้ไขด้วยมือจากหลายบรรทัดเหลือบรรทัดเดียว
  • ถ้า runner.php รันช้ากว่า 1 นาที (เช่น job ข้างในใช้เวลานาน) อาจมีการ trigger ซ้ำซ้อนได้ ถึงแม้โค้ดที่เขียนมีการเช็ค last_run_at กันไว้แล้วก็ตาม (ดู logic ใน หัวข้อ 5)

5. สิ่งที่สร้างจริง: cron_schedules + runner.php + Admin UI

โครงสร้างตาราง DB (ไฟล์ database/add_cron_schedules.sql):


cron_schedules
├── id
├── name              -- ชื่อ job ที่อ่านง่าย เช่น "PM2.5 Data Sync"
├── target_url         -- URL ที่จะยิง เช่น https://iservice.rangsitcity.go.th/pm25_cron.php
├── interval_minutes   -- ความถี่ เป็นนาที เช่น 15
├── is_active          -- เปิด/ปิดโดยไม่ต้องลบ
├── last_run_at        -- เวลาที่รันล่าสุด
├── last_status        -- success / error
├── last_http_code
└── last_message       -- เก็บ response body ส่วนต้น (ช่วยดัก warning จาก endpoint ปลายทางได้ — ดูตัวอย่างจริงด้านล่าง)

cron_schedule_runs       -- ตารางประวัติ เก็บทุกครั้งที่รัน (1-to-many กับ cron_schedules)
├── schedule_id (FK)
├── ran_at
├── status / http_code / message
└── duration_ms

หลักการตัดสินใจ "ถึงเวลาหรือยัง" ใน cron/runner.php — ใช้นาทีนับจาก Unix epoch หารด้วย interval แทนการดู date('i') เฉย ๆ เพื่อให้ใช้ได้ถูกต้องแม้ interval ไม่ใช่ตัวหารของ 60:


$minutesSinceEpoch = intdiv(time(), 60);
if ($minutesSinceEpoch % $interval !== 0) {
    continue; // ยังไม่ถึงเวลา
}
if (!empty($job['last_run_at']) && (time() - strtotime($job['last_run_at'])) < 50) {
    continue; // กันรันซ้ำในนาทีเดียวกัน
}

เคสจริงที่เจอตอนทดสอบ — runner ดักจับ PHP warning จาก endpoint ปลายทางได้ทันที เพราะเก็บ response body ทั้งก้อนไว้ดู (เดิมที cron-job.org ไม่โชว์รายละเอียดนี้เลย จึงไม่มีใครรู้ว่ามี warning ซ่อนอยู่หลายเดือน):


last_message: "Warning: file_put_contents(/var/www/html/iservice/storage/pm25_cron.log): Failed to open stream: Permission denied ..."

สาเหตุคือไฟล์ log เป็นของ rssc:rssc (permission 664) แต่ PHP ในคอนเทนเนอร์รันเป็น www-data (uid/gid 33) ซึ่งไม่ใช่ owner และไม่ใช่ group เดียวกัน เลยตกไปอยู่กลุ่ม "other" ที่อ่านได้อย่างเดียว แก้โดย:


sudo chown rssc:33 storage/pm25_cron.log   # ตั้ง group เป็น gid 33 (www-data ในคอนเทนเนอร์)
sudo chmod 664 storage/pm25_cron.log        # group มีสิทธิ์เขียนแล้ว

หน้า Admin UI (admin/cron_schedules.php) ใช้ pattern เดียวกับหน้า admin อื่นในโปรเจกต์ (เทียบกับ admin/pm25_api_keys.php) — ฟอร์ม POST ธรรมดาไม่ใช้ AJAX แยกไฟล์ API เพราะ logic ไม่ซับซ้อนพอที่จะคุ้มกับความซับซ้อนเพิ่ม: create / update / toggle / delete / run_now ล้วนเป็น POST handler ในไฟล์เดียวกัน ตามด้วย redirect หรือ render ตารางใหม่

7. บทเรียนที่ได้จากการลงมือทำจริง

  • cron ไม่ได้ "นับเวลา" แต่ "เช็คนาฬิกา" — เข้าใจตรงนี้แล้วจะตอบคำถามเรื่อง "ทำไมรันตรง :00 :15 :30 :45" ได้เอง ไม่ต้องจำเป็นกรณี ๆ ไป
  • คำสั่งที่แก้ไฟล์ระบบแบบ pattern-matching (เช่น sed) ต้องเจาะจงให้พอ — ไฟล์ crontab ของ user หนึ่งคนอาจมีหลายโปรเจกต์ปนกันอยู่ การแก้แบบ global replace มีโอกาสกระทบของคนอื่นโดยไม่ตั้งใจ
  • ระบบที่ "ดูเหมือนซ้ำกัน" อาจไม่ได้ซ้ำจริง — pm25_cron.php (iService/MariaDB) กับ pm25_cron.js (Next.js CDP/PostgreSQL) ทำงานคล้ายกันมาก แต่เป็นคนละระบบที่เลี้ยงคนละแอป ก่อนจะ "ยุบรวม" ของที่ดูซ้ำกัน ต้องเช็คให้แน่ใจก่อนว่าจริง ๆ ซ้ำหรือแค่หน้าตาคล้าย
  • เก็บ response/log แบบเต็ม ๆ มีค่ามากกว่าที่คิด — บั๊ก permission ของ log file ซ่อนอยู่มาหลายเดือนเพราะ cron-job.org ไม่โชว์ response body ให้เห็น พอเปลี่ยนมาเก็บ message เต็มใน DB ก็เจอปัญหาทันทีในการทดสอบครั้งแรก

8. เมื่อไหร่ควรใช้เครื่องมือสำเร็จรูปแทน

การสร้าง Virtual Cron เองมีไว้เพื่อ "เข้าใจหลักการ" ไม่ได้แปลว่าต้องสร้างเองทุกโปรเจกต์ตลอดไป เครื่องมือสำเร็จรูปที่ใช้หลักการเดียวกันนี้ (DB/queue-driven scheduler บน OS cron ตัวเดียว) และควรพิจารณาเมื่อความต้องการซับซ้อนขึ้น ได้แก่:

  • Laravel Task Scheduling — ถ้าโปรเจกต์เปลี่ยนไปใช้ Laravel framework เต็มรูปแบบ มีระบบนี้ในตัวอยู่แล้ว ไม่ต้องสร้าง runner.php เอง
  • n8n / Node-RED — ถ้าต้องการ workflow ที่ซับซ้อนกว่าแค่ "ยิง URL ตามเวลา" เช่น มีเงื่อนไข, retry, แจ้งเตือนผ่าน LINE/Email เมื่อ job ล้มเหลว
  • cron-job.org (กลับไปใช้ได้ถ้าจำเป็น) — ถ้าวันหนึ่ง VM1 ไม่มี cron daemon ให้ใช้เลย (เช่น ย้ายไป serverless/managed hosting ที่ควบคุม OS-level cron ไม่ได้) SaaS ภายนอกก็ยังเป็นตัวเลือกที่สมเหตุสมผล — สิ่งที่ได้จากการทำเองคือ เข้าใจว่าเครื่องมือสำเร็จรูปพวกนี้ทำอะไรอยู่ข้างหลัง ไม่ใช่แค่เชื่อตามที่มันบอก
