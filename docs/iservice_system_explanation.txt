==================================================================
ระบบ iService - บริการดิจิทัลของเทศบาลนครรังสิต
==================================================================
URL : https://iservice.rangsitcity.go.th/

ระบบรับคำขอบริการด้าน IT/ดิจิทัล ของเทศบาลนครรังสิต ให้ประชาชน/
บุคลากรเทศบาลยื่นคำขอออนไลน์ และให้แอดมิน/เจ้าหน้าที่บริหารจัดการ
มอบหมายงาน ติดตามสถานะ จนงานเสร็จสิ้น ครอบคลุม 9 ประเภทบริการ:

  1. EMAIL        - ขอ/รีเซ็ตอีเมลเทศบาล
  2. NAS           - ขอพื้นที่เก็บข้อมูล NAS
  3. IT_SUPPORT    - แจ้งซ่อมระบบ IT
  4. INTERNET      - ขอ/แก้ไขปัญหาอินเทอร์เน็ต
  5. QR_CODE       - สร้าง QR Code (บริการสาธารณะ ไม่ต้องกรอกข้อมูลผู้ขอ)
  6. PHOTOGRAPHY   - ขอบริการถ่ายภาพ/วิดีโอ
  7. WEB_DESIGN    - ออกแบบเว็บไซต์ / ปรับปรุงแก้ไข / update ข้อมูล
  8. PRINTER       - แจ้งซ่อม/ขอเครื่องพิมพ์
  9. LED           - ขอนำสื่อขึ้นจอ LED
 10. MC            - ขอพิธีกร

==================================================================
1. ภาพรวมระบบ (System Overview)
==================================================================
สถาปัตยกรรมเป็นแบบ "Form-driven, Service-code routing" คือมีฟอร์ม
กลางตัวเดียว (request-form.php) ที่โหลดชุด field ต่างกันตาม
service_code ที่ส่งมาทาง URL แล้วประมวลผลที่ปลายทางเดียวกัน
(api/process_request.php) ซึ่งจะ branch ตาม service_code อีกครั้ง
เพื่อบันทึกรายละเอียดเฉพาะของบริการนั้น ๆ ลงตารางย่อยของตัวเอง

แนวคิดออกแบบหลัก: "1 ตารางหลัก + ตารางลูกเฉพาะบริการ"
  - service_requests      = ข้อมูลกลางทุกคำขอ (ผู้ขอ, แผนก, สถานะ)
  - request_<service>_details = ข้อมูลเฉพาะของบริการนั้น (1:1 กับ
    service_requests ผ่าน request_id)

ผังการทำงานทั้งระบบ:

  ประชาชน/เจ้าหน้าที่
        |
   request-form.php  ?service=SERVICE_CODE
        | (ฟอร์ม dynamic ตามชนิดบริการ + CAPTCHA)
        v
   api/process_request.php (POST, transaction)
        | - gen request_code (REQ-YYYY-NNNN)
        | - insert service_requests
        | - insert request_<service>_details
        | - upload attachments -> storage/uploads/...
        | - ส่ง Email + LINE แจ้งเตือน
        v
   request-success.php?code=REQ-YYYY-NNNN
        |
        v
   tracking.php?req=REQ-YYYY-NNNN   <-- ประชาชนติดตามสถานะ
                                          (timeline 4-5 ขั้น)

   ฝั่งแอดมิน:
   admin/service_requests.php  (ดู/กรอง/มอบหมายงานทั้งหมด)
        -> admin/request_detail.php (มอบหมาย, เปลี่ยนสถานะ, พิมพ์)
              -> สร้างแถวใน task_assignments
   admin/my_tasks.php  (เจ้าหน้าที่ดูงานที่ตนได้รับมอบหมาย)

2. การออกแบบ (Design)
==================================================================

2.1 โครงสร้างฐานข้อมูล
-----------------------
ตารางหลัก:
  - service_requests       : คำขอกลาง (request_code, service_code,
    requester_*, department_id/name, subject, description,
    priority, status, expected_completion_date,
    attachments (JSON array ของ path ไฟล์), created_at, updated_at)
  - my_service              : master รายการบริการ 10 ชนิด
    (service_code, service_name, icon, color_code, display_order)
  - task_assignments        : การมอบหมายงาน (request_id,
    assigned_to, assigned_by, status, priority, due_date,
    accepted_at, started_at, completed_at, completion_notes)
    - รองรับ "หลายคนต่อ 1 คำขอ" (multi-assignee)
  - departments              : โครงสร้างหน่วยงาน 4 ระดับ
    (department_id, parent_department_id, level 1-4, level_type)
  - users                    : ผู้ใช้ระบบ (role: admin/staff/user,
    department_id, line_user_id สำหรับแจ้งเตือน)
  - prefixes                 : คำนำหน้าชื่อ (70+ รายการ)
  - system_settings           : ค่าคงที่ระบบ (LINE token, SMTP,
    ชื่อหน่วยงาน, โลโก้)

ตารางย่อยเฉพาะบริการ (1 ตาราง/บริการ ผูกกับ service_requests.id):
  request_email_details, request_nas_details,
  request_it_support_details, request_internet_details,
  request_qrcode_details, request_photography_details,
  request_webdesign_details, request_printer_details,
  request_mc_details, request_led_details

ข้อดีของการแยกตารางย่อย: เพิ่ม/แก้ field เฉพาะบริการได้โดยไม่
กระทบ schema กลาง, query รายงานสรุปทำได้ง่ายจาก service_requests
อย่างเดียว ส่วนรายละเอียดเจาะลึกค่อย JOIN เฉพาะตอนต้องใช้

2.2 สถานะงาน (Status Workflow)
-------------------------------
service_requests.status : pending -> in_progress -> completed
                           (หรือ cancelled / rejected)
task_assignments.status : pending -> accepted -> in_progress
                           -> completed (หรือ cancelled)

ความสัมพันธ์: คำขอ 1 รายการ อาจถูกมอบหมายหลายคน แต่ tracking.php
จะเลือกแสดง "งานที่คืบหน้าที่สุด" เป็นตัวแทนสถานะของขั้นตอนนั้น ๆ
(ORDER BY FIELD(status,'completed','in_progress','accepted',
'assigned') ASC)

3. เทคนิควิธีการ (Implementation Techniques)
==================================================================

3.1 Dynamic Form ต่อ Service Code
-----------------------------------
request-form.php รับ ?service=SERVICE_CODE แล้ว include ไฟล์
forms/service-form-fields-{SERVICE_CODE}.php เข้ามาแบบ partial
ฟิลด์ "ร่วม" ที่ทุกบริการมี (ยกเว้น QR_CODE ซึ่งเป็นบริการ
สาธารณะไม่ต้องระบุตัวผู้ขอ): คำนำหน้า/ชื่อ-สกุล, อีเมล/โทรศัพท์,
แผนกแบบ cascade dropdown 4 ระดับ (โหลดด้วย AJAX ตามลำดับ
สำนัก/กอง -> ส่วน -> ฝ่าย/กลุ่มงาน -> งาน), ตำแหน่ง, หมายเหตุ,
ไฟล์แนบ (สูงสุด 5 ไฟล์ รวม 10MB) และ CAPTCHA ภาพ
ฟิลด์ priority/target_date จะถูกซ่อนสำหรับบริการที่ไม่จำเป็นต้อง
ใช้ (EMAIL, INTERNET, PHOTOGRAPHY, MC, LED)

3.2 ความปลอดภัยตอนรับคำขอ
---------------------------
- CAPTCHA ภาพ ตรวจกับค่าใน $_SESSION ก่อนเข้า logic ใด ๆ
- ใช้ $conn->begin_transaction() ครอบทั้งกระบวนการ insert
  หลายตาราง ถ้า error ใด ๆ เกิดขึ้น rollback ทั้งหมด ไม่ปล่อยให้
  มีคำขอ "ครึ่ง ๆ กลาง ๆ" ในระบบ
- LINE user id ดึงจาก $_SESSION เท่านั้น (ไม่รับจาก POST ตรง ๆ)
  ป้องกันการปลอมแปลงผู้ส่ง

3.3 การสร้างเลขที่คำขอ (Request Code)
----------------------------------------
รูปแบบ REQ-{ปี}-{เลขรัน 4 หลัก} เช่น REQ-2026-0001 — หาเลขล่าสุด
ของปีนั้นด้วย LIKE 'REQ-{ปี}-%' แล้ว +1 พร้อม zero-pad

3.4 การจัดการไฟล์แนบ
----------------------
ไฟล์แนบทั่วไป: เก็บที่ storage/uploads/requests/{ปี}/{เดือน}/
  ตั้งชื่อใหม่ REQ_{uniqid}.{ext} กัน path traversal/ชื่อชนกัน
  จำกัดชนิดไฟล์ (jpg, png, pdf, doc, docx) และขนาด (5MB/ไฟล์)
  เก็บ path เป็น JSON array ไว้ในคอลัมน์ attachments
ไฟล์สื่อ LED: เก็บแยกที่ storage/uploads/led/{ปี}/{เดือน}/ รองรับ
  ไฟล์ใหญ่ถึง 200MB (วิดีโอ) หรือรับเป็นลิงก์ media_url
  (Google Drive/YouTube) แทนได้ ไม่ต้องอัปโหลดเข้าระบบ

3.5 การแจ้งเตือนอัตโนมัติ (Notification)
-------------------------------------------
หลัง insert สำเร็จ ระบบยิงแจ้งเตือน 4 ทาง พร้อมกัน:
  1. Email ถึงผู้ขอ (send_request_notification)
  2. Email ถึง admin/staff ทุกคนที่ active (notify_admins_new_request)
     - ดึงรายชื่อจาก users WHERE role IN ('admin','staff')
     - เนื้อหามีปุ่ม "จัดการคำร้อง" และ "ดูสถานะ" ฝังลิงก์ตรง
     - บน localhost จะไม่ส่งจริง แต่บันทึก log ลง
       storage/email_log.txt แทน (กันการส่งเมลผิดพลาดตอน dev)
  3. LINE แจ้งกลุ่ม (send_line_notification) - ใช้ group_id ที่
     ตั้งใน system_settings
  4. LINE ส่งตรงถึงผู้ขอ (send_line_to_requester) - ถ้ามีการผูก
     LINE ไว้ก่อนยื่นคำขอ (ผ่าน LINE Login ในหน้าฟอร์ม)
ทั้งหมดยิงผ่าน HTTP POST ไปยัง LINE Messaging API
(https://api.line.me/v2/bot/message/push) ด้วย Bearer token ที่
เก็บใน system_settings (key line_channel_token)

3.6 QR Code - กรณีพิเศษ (Client-side generation)
----------------------------------------------------
บริการ QR_CODE ต่างจากบริการอื่นตรงที่ "สร้างผลลัพธ์ที่ฝั่ง
เบราว์เซอร์" ด้วยไลบรารี QRCodeStyling (JS) ไม่ต้องรอ server
ประมวลผลภาพ ผู้ใช้เลือกชนิด (URL/text/vCard/WiFi/Payment), ขนาด,
สี, โลโก้ตรงกลาง แล้วเห็นพรีวิวสด ๆ ก่อนกดดาวน์โหลด PNG/SVG
ระบบเก็บแค่ log การใช้งาน (qr_usage_logs: ip, เวลา, พารามิเตอร์ที่
เลือก) ไม่ได้เก็บคำขอแบบบริการอื่นเพราะไม่ต้องมีการมอบหมายงานต่อ

==================================================================
4. เจาะลึกการทำงาน - ส่วนบริการ (Public-Facing Service Detail)
==================================================================

4.1 EMAIL - ขออีเมลเทศบาล
----------------------------
ฟิลด์: ชื่อ-สกุล (อังกฤษ), รูปแบบอีเมลที่ต้องการ, ประเภทคำขอ
(ขอใหม่ / รีเซ็ตรหัสผ่าน - สลับแสดงฟิลด์อีเมลเดิมถ้าเลือกรีเซ็ต),
วัตถุประสงค์การใช้งาน
เก็บที่ request_email_details: requested_username, email_format,
quota_mb (ค่าคงที่ 2048 MB ทุกคำขอ), is_new_account, existing_email,
purpose

4.2 NAS - พื้นที่เก็บข้อมูล
------------------------------
ฟิลด์: ชื่อโฟลเดอร์ที่ต้องการ, ขนาดพื้นที่ (dropdown 10GB-1000GB,
ค่าเริ่มต้น 100GB), ระดับสิทธิ์ (read_only/read_write/full_control),
ต้องการ backup หรือไม่, รายชื่อผู้ใช้ร่วม, วัตถุประสงค์
เก็บที่ request_nas_details

4.3 IT_SUPPORT - แจ้งซ่อมระบบ IT
------------------------------------
ฟิลด์: ประเภทปัญหา (hardware/software/network/other), ระดับความ
เร่งด่วน (low/medium/high/critical), ชนิด/ยี่ห้ออุปกรณ์, สถานที่
ตั้งอุปกรณ์, อาการที่พบ (textarea บังคับ), ข้อความ error, ช่วงเวลา
ที่เริ่มพบปัญหา
เก็บที่ request_it_support_details

4.4 INTERNET - อินเทอร์เน็ต
------------------------------
ฟิลด์: ประเภทคำขอ (ขอ WiFi ใหม่ / รีเซ็ตรหัสผ่าน / อื่น ๆ - ตัว
เลือกโหลดจากตาราง internet_request_types ที่แอดมินกำหนดได้),
สถานที่ติดตั้ง, รายละเอียดปัญหา (กรณีแก้ไข), เลขบัตรประชาชน
(auto-fill จาก session ถ้า login แล้ว)
เก็บที่ request_internet_details

4.5 QR_CODE - สร้าง QR Code
-------------------------------
(ดูรายละเอียดเทคนิคในหัวข้อ 3.6) เป็นบริการสาธารณะที่ใช้งานได้
ทันทีไม่ต้องกรอกข้อมูลผู้ขอ เพราะไม่มีขั้นตอนมอบหมายงานตามมา

4.6 PHOTOGRAPHY - บริการถ่ายภาพ
-----------------------------------
ฟิลด์: ชื่องาน/กิจกรรม, ประเภทงาน, วันที่จัดงาน (Flatpickr ปฏิทิน
ไทย), เวลาเริ่ม-เวลาสิ้นสุด (Flatpickr time picker 24 ชม.), สถานที่,
จำนวนช่างภาพที่ต้องการ (1-3 คน), รูปแบบไฟล์ที่ต้องการรับ (ค่าเริ่ม
ต้น "Digital (Google Drive)"), เลือกชนิดงาน (ภาพถ่าย/วิดีโอ ติ๊กได้
หลายอย่าง)
เก็บที่ request_photography_details — ไม่มีระบบ priority/แนบไฟล์/
หมายเหตุ เพราะไม่จำเป็นกับงานประเภทนี้

4.7 WEB_DESIGN - ออกแบบเว็บไซต์ / แก้ไข / update ข้อมูล
-----------------------------------------------------------
ฟิลด์: ประเภทเว็บไซต์ (เว็บหลัก/เว็บกอง/เพิ่มหน้า/ระบบใหม่), ชื่อ
โครงการ, วัตถุประสงค์, กลุ่มผู้ใช้เป้าหมาย, จำนวนหน้าโดยประมาณ,
ฟีเจอร์ที่ต้องการ (ข่าว/ฟอร์ม/แกลเลอรี/ค้นหา ฯลฯ), มีเว็บเดิมอยู่
แล้วหรือไม่ (ถ้ามีให้กรอก URL เดิม), ชื่อโดเมนที่ต้องการ, ต้องการ
hosting หรือไม่, เว็บไซต์ตัวอย่างอ้างอิง, ธีมสี, งบประมาณ, แนบไฟล์
(รองรับ drag-and-drop พร้อมลบไฟล์รายตัว)
เก็บที่ request_webdesign_details — ใช้สำหรับทั้งงาน "สร้างใหม่"
และ "ปรับปรุง/แก้ไข/update ข้อมูล" เว็บที่มีอยู่แล้ว แยกด้วยฟิลด์
website_type และ has_existing_site

4.8 PRINTER - เครื่องพิมพ์
-----------------------------
ฟิลด์: ประเภทปัญหา (ซ่อม/เปลี่ยนหมึก/กระดาษติด/ลงไดรเวอร์/ติดตั้ง
ใหม่/อื่น ๆ), ชนิดเครื่อง (inkjet/laser/multifunction/scanner/
plotter/3D), ยี่ห้อ/รุ่น/S-N, สถานที่ตั้งเครื่อง, รายละเอียดปัญหา,
รหัส error, สีหมึกที่ต้องการ, วัสดุสิ้นเปลืองที่ต้องการเพิ่ม
เก็บที่ request_printer_details

4.9 LED - ขอนำสื่อขึ้นจอ LED
--------------------------------
ฟิลด์: ชื่อสื่อ/เนื้อหา, วันที่เริ่ม-สิ้นสุดแสดงผล (Flatpickr,
ขั้นต่ำคือวันถัดไป), ประเภทสื่อ (ภาพ/วิดีโอ/animation), แหล่งสื่อ
เลือกได้ 2 ทาง คือ อัปโหลดไฟล์ (สูงสุด 200MB) หรือวางลิงก์
(Google Drive/OneDrive/YouTube)
เก็บที่ request_led_details (รวม duration_seconds ค่าเริ่มต้น
15 วินาที, resolution)

4.10 MC - ขอพิธีกร
----------------------
ฟิลด์: ชื่องาน/กิจกรรม, ประเภทงาน (พิธีการ/บันเทิง/สัมมนา/แถลงข่าว/
อื่น ๆ), สถานที่, วันที่-เวลาเริ่ม-เวลาสิ้นสุด (Flatpickr ปฏิทินไทย
+ time picker), จำนวนพิธีกรที่ต้องการ (1-10 คน), ภาษา (ไทย/อังกฤษ/
ทั้งสอง), สถานะสคริปต์ (ยังไม่พร้อม/ร่างแล้ว/พร้อมแล้ว), การแต่งกาย
ที่กำหนด, แนบไฟล์เอกสารกำหนดการ (บังคับแนบ รองรับ drag-and-drop)
เก็บที่ request_mc_details

==================================================================
5. เจาะลึกการทำงาน - ส่วนบริหารจัดการ (Admin Management Detail)
==================================================================

5.1 รายการคำขอกลาง (admin/service_requests.php)
----------------------------------------------------
หน้ารวมคำขอทุกบริการทุกประเภท แอดมินกรองตามสถานะ/ประเภทบริการ/
แผนก/ช่วงวันที่ ได้ จากที่นี่กดเข้าไปดูรายละเอียดและกดมอบหมายงาน
ได้ทันที

5.2 โครงสร้างหน่วยงาน 4 ระดับ (admin/departments.php)
----------------------------------------------------------
สำนัก/กอง -> ส่วน -> ฝ่าย/กลุ่มงาน -> งาน
เก็บในตาราง departments แบบ self-reference (parent_department_id)

5.3 การมอบหมายงาน (admin/request_detail.php)
--------------------------------------------------
แอดมินเปิดดูคำขอ แล้วเลือกผู้รับผิดชอบผ่าน chip-picker แบบเลือกได้
หลายคนต่อ 1 คำขอ (multi-assignee) — กดมอบหมายแล้วระบบสร้างแถวใหม่
ใน task_assignments ต่อคนที่เลือก (1 คำขออาจมีหลายแถว task_assignments)
พร้อมส่ง LINE แจ้งเตือนรายบุคคลให้ผู้ที่ได้รับมอบหมายทุกคน
หน้านี้ยังสลับโหมดดู/แก้ไขได้ และมีปุ่มพิมพ์ (เปิด
admin/request_print.php หน้า A4 พร้อมโลโก้เทศบาล)

5.4 งานของฉัน (admin/my_tasks.php)
---------------------------------------
เจ้าหน้าที่ดูรายการงานที่ตนได้รับมอบหมาย แบ่งตามสถานะเป็นแท็บ
(รอรับงาน/กำลังดำเนินการ/เสร็จสิ้น) งานที่ถูกยกเลิกแยกไปอยู่แท็บ
สุดท้ายต่างหาก ไม่ปนกับงานที่ยังดำเนินการอยู่ เจ้าหน้าที่กด
รับงาน/เริ่มงาน/ปิดงาน เพื่ออัปเดต task_assignments.status ซึ่งจะ
สะท้อนไปที่ timeline ของ tracking.php โดยอัตโนมัติ

5.5 การติดตามสถานะของประชาชน (tracking.php)
--------------------------------------------------
ประชาชนกรอกเลขที่คำขอ (REQ-YYYY-NNNN) ระบบแสดง timeline แนวตั้ง
4-5 ขั้นตอน:
  1. รับเรื่อง       - เสร็จเสมอ (เวลา = created_at ของคำขอ)
  2. มอบหมายงาน      - เสร็จเมื่อมีแถวใน task_assignments แล้ว
                       (แสดงชื่อผู้รับมอบหมายทุกคนคั่นด้วยจุลภาค)
  3. รับงาน          - เสร็จเมื่อสถานะ task เป็น accepted ขึ้นไป
  4. กำลังดำเนินการ  - เสร็จเมื่อสถานะ task เป็น in_progress ขึ้นไป
  5. เสร็จสิ้น/ถูกปฏิเสธ - ตามสถานะสุดท้ายของคำขอ
ถ้ามีผู้รับมอบหมายหลายคน ระบบเลือกแสดง "งานที่คืบหน้าที่สุด" เป็น
ตัวแทนแต่ละขั้น เพื่อไม่ให้ timeline สับสนเวลามีคนทำงานช้า-เร็ว
ต่างกัน
มีหน้า tracking_print.php สำหรับพิมพ์ใบติดตามเป็น PDF/A4 พร้อม
QR Code ลิงก์กลับมาที่หน้าติดตามนี้

5.6 การแจ้งเตือนฝั่งแอดมิน
-----------------------------
ตาราง service_notification_emails กำหนดได้ว่าบริการไหนแจ้งไปที่
อีเมลใครเป็นพิเศษ (นอกเหนือจากอีเมล admin/staff ทุกคนที่ active)
เช่น งาน MC และ PHOTOGRAPHY แจ้งเพิ่มไปที่อีเมลเจ้าหน้าที่
ประชาสัมพันธ์โดยเฉพาะ ทำให้หน่วยงานที่เกี่ยวข้องได้รับทราบทันทีโดย
ไม่ต้องรอแอดมินกลางส่งต่อ
